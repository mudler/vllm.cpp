## Problem

AGENTS.md Gates admits a performance result from an arm only after that arm's declared token-exact gate passes. The `qwen4_exp` ROCm arm has no such gate — not a failing one, an ABSENT one. **THE SENTENCE THAT STOOD HERE WAS FALSE AND IS REPLACED RATHER THAN AMENDED.** It read: "it cannot simply be written, because the architecture has no primary oracle: `Qwen/Qwen3.8-Flash-Next` declares `Qwen4ExpForConditionalGeneration` / `qwen4_exp`, which no vLLM revision implements (#1978)". **vLLM implements this architecture in full at the ACTIVE parity pin** `e126687a9a828d513c01a07cd69f025f27d63280` (`[Model] Support Qwen3.8-Flash-Next (#53896)`, 2026-08-31), and the row's own spec recorded the reconciliation on 2026-09-01: `.agents/specs/qwen4-exp-flash-next.md:85` states "vLLM is this row's primary oracle from 2026-08-31" and its component table at `:169-218` cites `e126687a9a` line by line. Read at that revision, `vllm/models/qwen4_exp/` carries a shared `common/`, a `config.py` and two COMPLETE backends, `nvidia/` and `amd/`: the decoder layer and its forward at `vllm/models/qwen4_exp/nvidia/model.py:174` and `:274`, the hyper-connection at `nvidia/hyperconnection.py:50` over five Triton kernels in `nvidia/ops/hc.py`, QSA, PLE and MTP beside them. The registry carries `Qwen4ExpForCausalLM` (`vllm/model_executor/models/registry.py:114`), **`Qwen4ExpForConditionalGeneration` — the class THIS ROW PORTS — at `:580`** (`nvidia/model.py:841`, the Qwen3-VL tower over a `Qwen4ExpForCausalLM` language model at `:922`), and `Qwen4ExpMTP` at `:670`. Nothing about this is a stub or a name reservation. **#1978 is not wrong, it is EXPIRED**: it was read live against vLLM `origin/main` = `6a5e8f5979` on 2026-08-26, five days before the support landed, and the spec records that expiry at `:110-126`.

**A primary oracle therefore EXISTS and can define token-exact. What is missing is a RUN, and the three blockers are specific.** (1) `.agents/oracles/vllm.md` records that `qwen4_exp` does not run on this fleet at this revision: the QSA indexer's `cooperative_topk` refuses to launch with a cluster misconfiguration ([#2626](https://github.com/mudler/vllm.cpp/issues/2626), cause unestablished). (2) Every published safetensors arm exceeds the largest fleet box (official FP8 ~180 GB, NVFP4 ~128 GB, against 119.631 GiB on `dgx:gpu0`), and vLLM reads safetensors, not GGUF — the 67.564 GiB UD-IQ1_S artifact this row measures is not a file the in-tree loader can open. (3) The NVIDIA decode GEMM plan is `sm_103`-gated (`nvidia/low_latency_gemm.py:82-83`), which is neither `sm_121a` nor gfx1151; that costs speed rather than tokens, but it is part of the recipe. The one candidate path that clears blocker (2) on gfx1151 is `vllm-gguf-plugin`, whose own oracle record reads `gateable = yes` on that board since 2026-09-10 — whether it maps a `qwen4exp` GGUF onto vLLM's `Qwen4ExpForConditionalGeneration` is UNREAD and is the next thing to establish. The pinned secondary oracle `llama-cpp-qwen4exp` (ggml-org/llama.cpp PR #27742 at 035e22731a7fd70b9854b3a2d64ec68e9b1a45d3) now BUILDS with HIP for gfx1151 and DECODES the released UD-IQ1_S artifact on strix:gpu0, so a llama.cpp denominator exists on that board (docs/bench-evidence/qwen4exp-llamacpp-denominator-gfx1151-20260913.md, #2060). A denominator is a single-engine fact and needs no gate. A RATIO does, and this issue owns the missing precondition. Two further obstacles are specific rather than general. llama.cpp's own decode here is not token-gated against anything either, and the oracle record states its greedy decode is not deterministic across its own kernel paths. And the two engines are not serving the same surface: /props at the pin reports modalities vision=false video=false audio=false, so the llama.cpp arm is TEXT ONLY while MODEL-MM-QWEN4-EXP is a multimodal port. Until a gate is declared and ratified, every qwen4_exp gfx1151 number is reported per engine and never divided. #2497 already carries one retraction for taking a cross-engine number ahead of that gate.
