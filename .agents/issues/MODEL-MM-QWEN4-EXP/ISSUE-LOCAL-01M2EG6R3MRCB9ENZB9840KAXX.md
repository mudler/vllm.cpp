## Problem

MEASURED FROM THE COMMITTED MANIFEST of the real artifact's GGUF headers,
`tests/vllm/models/qwen4_exp_gguf_manifest.inc`, generated by
`scripts/gen-qwen4-exp-gguf-manifest.py` from
`unsloth/Qwen3.8-Flash-Next-GGUF` UD-IQ1_S at revision
`8bdc666649440e9bdc97e16f3f75782c98478ff5`. No network call and no lease was
needed; the answer was already in the tree.

**1,225 tensor entries, and ZERO carry an MTP head.** No name matches `mtp`,
`nextn`, `draft`, `eh_proj`, `enorm` or `hnorm`. The only top-level prefixes are
`blk.`, `output.`, `output_hc_down.`, `output_hc_norm.`, `output_hc_up.`,
`per_layer_token_embd.` and `token_embd.`.

**AND THE BLOCK COUNT CONFIRMS IT INDEPENDENTLY, which is the check that closes
the question.** The manifest carries `blk.0` through `blk.47` and nothing higher
-- exactly the 48 trunk layers `Qwen4ExpParams::num_hidden_layers` declares.
llama.cpp's converter does not emit an MTP head under an `mtp.*` name: it writes
`<arch>.nextn_predict_layers` and FOLDS THE HEAD BLOCKS INTO `block_count`, which
is precisely why our own Qwen3.5 GGUF path subtracts it
(`qwen3_5_gguf_weights.cpp:965-974`: "llama.cpp's converter writes it as
`<arch>.nextn_predict_layers` and folds the head blocks into block_count, which is
why the trunk layer count above subtracts it"). A folded head would therefore
appear as `blk.48.*`. There is none. So the head is absent by both the naming
convention and the counting convention.

## Why this matters, and it is not a code gap

The architecture HAS an MTP head: `qwen4_exp.cpp:549` parses
`mtp_num_hidden_layers` and `qwen4_exp.h:229` documents its value as 1, and
`qwen4_exp_registry.cpp:16-20` explains that upstream carries it as an `mtp` block
inside the same text config rather than as a second registered architecture.

The ENGINE also already supports the exact configuration the reference runs.
`include/vllm.h:441-450` documents `{"method":"mtp","num_speculative_tokens":3}`,
with the depth defaulting to the checkpoint's `mtp_num_hidden_layers`. **But the
same paragraph states the limit: "Only MTP is supported today, on the Qwen3.5/3.6
checkpoints that ship an `mtp.*` head (safetensors only)."**

So there are three independent gaps and only one of them is ours to close by
writing code:

| | state |
|---|---|
| architecture defines an MTP head | YES |
| engine implements MTP speculative decoding | YES, safetensors only |
| **the released GGUF carries the head** | **NO -- the bytes are absent** |
| GGUF MTP loading for `qwen4exp` | not implemented |

**THE REFERENCE'S MAIN SPEED LEVER IS THEREFORE UNAVAILABLE ON THIS ARTIFACT.**
`.agents/specs/qwen4-exp-flash-next.md` records sojufx sparkDash C1 at 66.17 tok/s
running "MTP speculative decoding (K=3), FP8 KV cache, 8-seq scheduler" against
our 13.02 tok/s with no speculation. A K=3 MTP head is commonly worth 2-3x on this
shape of workload. We cannot switch it on, and not because it is unimplemented --
because the weights are not in the file.

## What this does and does not establish

**DOES NOT establish a ceiling.** This row's own rule is that an apparent
same-architecture limit is an unresolved implementation difference, and the
measured decode profile still has untraced terms -- notably QSA's ~1 ms per launch
that does not scale with context
(`ISSUE-LOCAL-01M2DQHP2FWXHH7GTHB17QX53Q` and the spec section it points at).

**DOES establish the arithmetic that any plan has to clear.** The reference
workload step is 87.6 ms at 88% GPU-busy; 66.17 tok/s is a 15.1 ms step. That is
**5.8x less step time**, against a profile whose two largest kernels are
`QsaGatherAttentionKernel` at 18.16 ms and cuBLAS `gemvx` at 17.53 ms per step.
Deleting BOTH entirely leaves ~52 ms, i.e. ~19 tok/s. No combination of the
identified kernel leads reaches 66 on this artifact without speculation.

## Owed, and it needs a decision rather than an implementer

Three routes exist and each has a cost this issue states rather than assumes:

1. **Convert an MTP-carrying GGUF ourselves** -- **ROUTE CLOSED, and it was the
   first thing checked.** The pinned `llama-cpp-qwen4exp` converter (PR #27742,
   head `6c5afc86ae84448ae4d744e357017e2c490ad9c3`) is the ONLY llama.cpp that
   converts this architecture, and `conversion/qwen4exp.py:29-31` refuses the
   head by construction:

   ```python
   # the MTP block is a separate draft head; vLLM drops it too
   supports_mtp_export = False
   no_mtp = True
   ```

   So the absence in the released artifact is not an oversight by whoever ran the
   conversion: **no GGUF produced by the only available converter can carry this
   head**, by that converter's explicit design, on the stated grounds that vLLM
   drops it too. Producing one would mean patching the converter, which puts a
   second unmerged-PR delta under a measurement, and then running a conversion
   whose own comment at `:151` records the PLE table alone peaking "near 300 GB of
   RSS" -- more than this fleet's largest box. Fetched by `curl` from the pinned
   head, a source read and not an asset download.
2. **Implement GGUF MTP loading for `qwen4exp`** -- necessary for route 1 to be
   usable, since the engine's MTP path is safetensors-only today. Useless on its
   own while the artifact lacks the head.
3. **Change the bar.** The comparison is already across different quantizations
   (NVFP4 ~128 GB against UD-IQ1_S ~68 GB) and different KV dtypes, which the
   spec's own result table flags as "directional, not a parity result". A
   same-artifact or same-feature-set comparison is a different and possibly more
   honest target.

Route 1 being closed makes route 2 **dead code by construction** -- a GGUF MTP
loader with no GGUF in existence that carries MTP weights -- so it must not be
scoped. That leaves route 3, a decision rather than an implementation, and the
honest framing of the gap: **on this artifact the reference's principal lever is
not reproducible with the tooling that exists**, and the comparison is measuring
two different feature sets rather than two implementations of one.
