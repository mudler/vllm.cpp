## Scope

Raise Qwen3.5-4B Q4_K_M text-generation throughput on the RX 7900 XTX
(gfx1100, RDNA3, 24 GiB, `rocm-dev:7.14.0`) to **>= 200 tok/s** under the
acceptance gate below, pure autoregressive greedy decode, single stream,
batch 1. No MTP or speculative decoding in any measurement arm. Owning
matrix row: `BACKEND-ROCM`.

Feasibility is SETTLED and is not relitigated inside the campaign:

- llama.cpp sustains ~200 tok/s on this exact checkpoint on this exact GPU
  with a q8 KV cache. The target is demonstrated on identical hardware.
- This engine's own lm_head kernel streams weights at ~598 GB/s on this
  board (TG150 evidence): the memory system delivers.
- Ceiling arithmetic: ~960 GB/s peak / ~2.2 GB per token ~= 430 tok/s
  theoretical, so 200 tok/s sits at ~47% of peak.

Therefore no stage may propose lowering the number, re-argue feasibility,
or pad reports with activity in place of measured position.

## Acceptance gate

Median of >= 5 repetitions, idle host, gpu-ctl lock held for the whole
window, batch 1, one ~512-token real prompt, 256 generated tokens, greedy
(`--temperature 0 --seed 0`), through the production entry point
(`examples/vllm-cli`). Recorded axes: output tok/s (the gated number),
steady-state TPOT, peak VRAM. A run under co-tenancy is provisional and
never satisfies this gate. Token identity: the 256-token output on the gate
prompt must be byte-identical to the pre-campaign output on the same build
config for every lever claiming bit-exactness; any lever that changes
reduction order records near-tie adjudication per the ratified band
doctrine (`.agents/specs/rocm-m4-oracle.md`) rather than asserting identity
it cannot show.

### T4a: opt-in MMVQ K-quant decode GEMV

Issue [#2789](https://github.com/mudler/vllm.cpp/issues/2789) reconstructs the
contributor's `VT_GEMV_MMVQ` arm for dense `m == 1` Q4_K, Q5_K, and Q6_K
decode. The unset environment variable keeps the current baseline route. The
arm accepts bf16 and f16 activations and writes bf16 or f32 outputs. Other M
values and grouped calls keep the current GDN routes.

`VT_GEMV_MMVQ_FOLD_MAX` controls the inclusive fold crossover. The default is
512 rows. A positive integer selects another limit. An empty, malformed,
nonpositive, or overflowing value uses the default.

The focused host gate tests the route policy, the M gate, and the fold
crossover. The HIP gate tests production route counters, output identity for
the activation and output types, and grouped delegation.

### T4b: opt-in fused RMSNorm Q8_K production

Issue [#2791](https://github.com/mudler/vllm.cpp/issues/2791) reconstructs only
the contributor leaf `b8ee53edf64c7afd72950f4e4c3d450692a99e71`, relative
to parent `8116aa7b340e9cfd054fe782134c13d758cc18fe`. Exact
`VT_NORM_QUANT_FUSED=1` lets the production ROCm `vt::RmsNorm` path emit Q8_K
activation scratch. The next matching dense `vt::MatmulBTQuant` K-quant call
on the same queue consumes that scratch once. An unset, empty, or different
value keeps the current standalone quantization route.

The producer token binds the output pointer, row count, hidden size, row
stride, output dtype, device index, queue ID, stream, scratch pointer, scratch
capacity, and the producing host thread. The token is one-shot. Every consume
attempt invalidates it, including a pointer, shape, stride, dtype, device,
queue, stream, or thread mismatch. This rule prevents stale, cross-queue, and
concurrent reuse. The queue-owned scratch pool retires old allocations and
never frees pointers that a captured graph can retain. A cold graph capture
refuses before allocation. A warm capture reuses the stable pointer without a
runtime capture query.

The producer accepts only contiguous RMSNorm outputs whose hidden size is a
positive multiple of 256 and whose Q8_K block count fits the 256-thread row
kernel. The existing ROCm RMSNorm path emits f32 or bf16, so those are the
producer dtypes. An f16 consumer cannot match a producer token and keeps the
standalone route. Other shapes, strides, and dtypes keep the baseline route.

T4a retains priority when `VT_GEMV_MMVQ` selects its fused LDS prologue. That
path invalidates any pending norm token and otherwise remains unchanged.
Grouped K-quant calls never consume this dense token. T4b does not change the
default, enable `VT_SKINNY_BF16`, or make a performance claim.

The focused gate enters the production `vt::RmsNorm` and
`vt::MatmulBTQuant` seams. It compares the emitted Q8_K bytes with standalone
quantization and the CPU oracle for random, tied-maximum, and all-zero rows.
It covers f32 and bf16 producer outputs, the f16 consumer fallback, default
off, one-shot reuse, stale and mismatched tokens, M, shape, stride, dtype,
device, queue, stream, host-thread boundaries, and cold and warm capture.
Host-side route counters are test witnesses only. The fresh reviewer deletes
the production producer call and consumer reuse branch separately; each
mutation must fail the focused gate.

The operator gated immutable head
`ad55eb8fff80cafc542a6bebc46eb5e47d099de5` in `rc` job
`3f3462c2-9ca3-4130-8bcb-f2d08c64e176`. The exact source archive has SHA-256
`a27f1e0fd7a980bca1d989aee1262e3abb870cb8b50e7e466208a77c159f1b58`.
The job ran on `strix:gpu0`, a Radeon 8060S at `gfx1151`. It used ROCm 7.2.4
and HIP 7.2.53211.

The clean Release HIP build completed 581 of 581 steps. The focused fused
norm-quant gate passed 3 of 3 cases and 62 of 62 assertions. The full

Restricting the consumer reuse branch to Q4_K caused four Q5_K and Q6_K

## Correctness policy

- The keep-quant integer core stays bit-exact vs CPU;
  `tests/vt/test_rocm_quant_dot.cpp` runs unchanged as the gate for every
  quant-path lever.
- Token coherence asserted on every A/B; byte-identical outputs claimed
  only for bit-exact levers.
- Any reduction-order change records near-tie adjudication with
  teacher-forced logprob gaps per the ratified band doctrine; a raw
  divergence count is never presented as a quality score.
- No checker is weakened; a gate that goes red names the repair.

## Risks

- R1: the pre-merge budget table misprices the tip (the three landed
  upstream levers change the ranking). T1 exists to price this first.
- R2: HIP graph capture may refuse a step containing a host-dependent op;
  fallback is FusedChain recipe reduction and a partial capture is
  recorded, not hidden.
- R3: 200 tok/s may require levers beyond kernels (scheduler, sampler
  sync). The campaign reports the measured position honestly; no ceiling is
  declared and a shortfall names the next traceable hypothesis.
