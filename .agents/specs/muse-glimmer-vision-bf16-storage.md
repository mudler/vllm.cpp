# Muse Glimmer's perception encoder — bf16 storage, and the golden that blocks it

Issue: [#2166](https://github.com/mudler/vllm.cpp/issues/2166).
Row: `ENG-MM-INPUT-PIPELINE` ([engine-matrix.md](../engine-matrix.md)).
Parent spec: [`vision-tower-dtype-polarity.md`](vision-tower-dtype-polarity.md),
which owns [#1359](https://github.com/mudler/vllm.cpp/issues/1359) and declared
the memory axis. Its Qwen3-VL half landed at `525d2b991` and is MEASURED; its
Muse Glimmer half did not land, and this spec owns why and what unblocks it.

**This spec does not re-declare the memory threshold.** The parent's §6.1 is the
declaring surface for both kinds; §5 below CONFIRMS the `muse-glimmer` figure by
re-deriving it two independent ways and cites the parent rather than restating
it. One fact, one document.

**Why a separate spec and not an extension of the parent.** The parent answers
"is the widening removable" — a storage question, answered `yes` and landed on
four of six towers. This row answers a different question with a different
failure mode: "how do we know a REGENERATED golden is correct rather than merely
current". That argument needs its own red-first evidence and its own
pre-declared numbers, and burying it inside a 732-line document that already
records a landed result would make the one unlanded half harder to find, not
easier. The parent stays the surface for the dtype policy and the memory axis;
this file is the surface for the fixture and its golden.

Written BEFORE the implementation. Every threshold in §6 is declared before the
implementing wave's first number exists. Do not edit a threshold after reading a
result.

## 0. The one-line answer

**Round the fixture's synthetic weights through bf16 once at generation, on both
sides, and regenerate the golden from the reference generator.** The f32 arm
then returns to its ~1e-7 residual by construction rather than by tolerance,
because the two sides hold bit-identical weight values again — the property the
fixture has always relied on and that the storage change breaks. The golden's
authority stays where it is today, in
`scripts/mm/muse_glimmer_vision_ref.py`'s verbatim transcription of upstream,
and never moves to our C++ output.

The regeneration is not a re-recording. **Twelve of the seventeen golden arrays
must come back byte-identical** and the five that move must move by exactly the
five figures §4.2 measures. That is a falsifiable gate on the regeneration
itself, and it is what separates this from a golden that cannot fail.

## 3. The block, verified rather than inherited

The parent spec's `## Now` records the block. This section re-establishes it
from the tree, because the parent's §4.4 ruling and its refutation are the exact
pair a fresh implementer must not take on trust.

### 3.1 The mechanism

`Upload` (`src/vllm/model_executor/models/muse_glimmer_vision.cpp:115-123`)
branches on `cfg.compute_dtype` (`:444`, `:725`):

```cpp
if (dt == DType::kBF16) {
  const std::vector<uint16_t> bf = ToBf16(host);   // F32ToBF16 per element
  return Buf(b, q, dt, shape, bf.data());
}
return Buf(b, q, dt, shape, host.data());          // kF32: the STORED values
```

The `kF32` arm uploads the stored host values unchanged. Its arithmetic is
therefore performed on whatever the store holds, which is why narrowing the
store moves it and why narrowing the store cannot move the `kBF16` arm.

The parent §3.1's ruling — that widening back is bit-identical because "the
values originated bf16" — is TRUE for the loader and FALSE for the fixture:

- **Loader.** `Bf16TensorToF32`
  (`src/vllm/model_executor/models/muse_glimmer_weights.cpp:651-675`) asserts
  `t.dtype == "BF16"` at `:654-655` and produces `BF16ToF32(bits)`. Every stored
  value is the image of a bf16 pattern, so `F32ToBF16` returns that pattern
  again. Verified EXHAUSTIVELY here rather than argued: applying
  `vt::F32ToBF16` — `src/vt/dtype.cpp:292-299`; `:266-290` is `F32ToF16` and is
  a DIFFERENT function — to all **65,280 finite** bf16 patterns via
  `vt::BF16ToF32` and back gives **0 failures**. "Finite" is load-bearing and
  is not a rounding of 65,536: the 256 patterns with `exp == 0xFF` are inf and
  NaN, and 126 of them do NOT round-trip, because `:294-296` sets the quiet bit
  on a NaN. No weight is one, so nothing this row claims depends on them.
  **Name the function, then the line.** `BF16ToF32` was still in
  `src/vt/dtype.cpp` when this row opened and is now
  `include/vt/dtype.h:244`, moved there inline by #2376 while `F32ToBF16`
  stayed behind and slid 51 lines up its own file. A line number in this pair
  of files has a short half-life.
- **Fixture.** `Weights.__init__`
  (`scripts/mm/muse_glimmer_vision_ref.py:278-312`) builds every weight from
  `lcg()` (`:52-61`), which returns `torch.float32` and never rounds through
  bf16. `FixtureWeights` (`tests/vllm/models/test_muse_glimmer_vision.cpp:84-113`)
  mirrors that recurrence bit-exactly. These are genuine 24-bit values, and
  narrowing the store genuinely moves them.

### 3.2 The five red assertions, reproduced without a build

The C++ arm could not be run — this investigation built nothing (§10). It did
not need to. The C++ f32 arm agrees with the torch reference to ~1e-7 today, so
the discrepancy the storage change introduces is, to three significant figures,
a property of the REFERENCE side alone: `ref_f32(round_bf16(W))` against
`ref_f32(W)`. That is computable in torch on this host in seconds.

Measured on `torch 2.11.0+cu130`, CPU, `OMP_NUM_THREADS=1`, by re-running the
committed generator's own `encoder_forward` twice — once with its weights as
built, once with every bf16-storage weight rounded through bf16 (`pos_emb` and
the pixel values deliberately not rounded):

| Stage | assertion | bound | rel_l2 | max_abs |
|---|---|---:|---:|---:|
| `ln_pre` image 0 | `test_muse_glimmer_vision.cpp:316` | `1e-6` | **2.220e-03** | 9.811e-03 |
| `ln_pre` image 1 | `:320` | `1e-6` | **2.164e-03** | 8.958e-03 |
| `block0` | `:325` | `1e-6` | **2.193e-03** | 9.625e-03 |
| tower out | `:330` | `1e-6` | **2.892e-03** | 1.349e-02 |
| adapter out | `:337` | `1e-6` | **3.462e-03** | 6.459e-04 |

Those are the same five figures the earlier wave measured on a scratch tree with
the C++ store actually narrowed, to every digit it recorded. Two independent
routes — one that built the change, one that did not — agree, which is what makes
the mechanism established rather than plausible.

The magnitude is also the one bf16 predicts and not a surprise: the per-tensor
weight perturbation `rel_l2(round_bf16(W), W)` measures 1.622e-03 to 1.922e-03
across `conv1`, `ln_pre_w`, `blk0.qkv_w`, `blk0.fc_w` and `ad_fc`, against a
half-ulp bound of `2^-9 = 1.95e-03`. The stage figures grow from 2.2e-03 at
`ln_pre` to 3.5e-03 at the adapter, which is accumulation over three blocks plus
the adapter. Nothing here is a defect; the fixture is simply being asked to
agree on values the two sides no longer share.

**Control.** `pos_emb` is not rounded, and its captured stage reads
`rel_l2=0.000e+00 max_abs=0.000e+00`. The perturbation reaches exactly the
tensors it was applied to.

### 3.3 The production arm is genuinely unaffected

`Upload`'s `kBF16` arm computes `F32ToBF16(stored)`. With bf16 storage it copies
`stored` directly. Since the loader's stored value is `BF16ToF32(b)` and the
round trip is exact (§3.1, 0 failures over 65,280 finite patterns), the device bytes are
identical. The earlier wave measured this rather than assuming it: in a tree with
the store narrowed, the bf16 arm read `rel_l2=5.951e-03 max_abs=3.675e-02`,
byte-for-byte what it reads today.

So the 3.5797 GiB widening is removable and only the fixture stands in the way.

## 4. The golden-correctness argument

This is the section the row exists for. Regenerating a golden is how a
regression gets hidden: a golden that records whatever the new code produces
cannot fail, and a green run then measures nothing. Three shapes were weighed.

### 4.1 What was rejected, and why

**Rejected — regenerate from the reference, leaving the fixture f32.** This is
not an alternative to §4.2; it is a null operation. The reference is unchanged,
so the regenerated golden is byte-identical to the committed one and the f32 arm
still reads 2.2e-03 against `1e-6`. The only way to make it green is to widen
the bound to about `1e-2` — at which point the f32 arm no longer discriminates
anything the bf16 arm's `2e-2` does not already, and the near-machine-epsilon
algorithm gate that catches a transposed patch layout, a swapped RoPE axis or a
mis-ordered qkv fold is simply gone. That is the "gate got weaker" failure
stated plainly, and it is refused.

**Rejected — narrow only where the values originated bf16.** The loader and the
fixture write into the SAME field. A field cannot be `uint16_t` for one writer
and `float` for the other without a second storage representation, which
AGENTS.md §"Shared seams" forbids ("Never write a parallel path by hand"). The
remaining readings of this option are "do not fix Muse Glimmer", which abandons
3.5797 GiB, or today's blocked state.

**Rejected — delete the `kF32` arm and gate bf16 only.** Same loss of the
near-epsilon gate, with the additional cost that the parent §4.4's reason for
keeping the `kF32` branch alive at all disappears with it.

**Rejected — regenerate the golden from our C++ output.** Named here so that no
implementing wave reaches for it. The generator is the authority. A golden taken
from the implementation it gates is the defect this section exists to prevent.

### 4.2 What is adopted: round the fixture's weights through bf16, once, on both sides

Change `scripts/mm/muse_glimmer_vision_ref.py` so that every synthetic weight
that becomes bf16 STORAGE is rounded once through bf16 at construction, and
mirror that in `FixtureWeights` / `FixtureAdapter` — where, on the C++ side, the
type change forces it anyway. `pos_emb` and the pixel values are NOT rounded:
the parent §4.3 keeps the positional table host-f32, and pixels are activations.

**Why this is correct and not merely current.**

1. **The authority does not move.** The golden is still produced by
   `muse_glimmer_vision_ref.py`, still a verbatim transcription of
   `muse_glimmer.py:555-1044` at `075d645af`, still in torch, still independent
   of our C++. The diff to the generator is a rounding of its own synthetic
   inputs; it touches no transcribed function.
2. **The weight values are the same on both sides again — bit-identical, not
   close.** The fixture's whole design is that both sides hold identical bits
   without shipping a weight blob. That property is what the storage change
   breaks and what this restores. It is checked and not assumed: applying the
   `vt::F32ToBF16` integer formula (`src/vt/dtype.cpp:292-299`) to all **25,712**
   fixture weight values across **43** tensors and comparing against
   `torch.Tensor.to(bfloat16)` gives **0 mismatches**. That population is the
   bf16-STORAGE set: `pos_emb`'s 512 values are excluded because this section
   does not round them, so the whole fixture is 44 tensors / 26,224 values, and
   26,192 was neither figure. Both are round-to-nearest-even, and they agree
   here in fact, not only in intent.
3. **The f32 arm therefore returns to its residual by construction.** With
   identical weight values on both sides and f32 arithmetic on both sides, the
   only remaining difference is accumulation order — exactly today's ~1e-7. The
   `1e-6` bound is not relaxed by one digit.
4. **Nothing the fixture tests is a property of the weights' low mantissa
   bits.** The stage assertions catch layout, ordering, convention and masking
   defects, each of which moves an output by O(1) relative. The values are an
   LCG; they carry no meaning and are not the checkpoint's. Their only
   requirements are pseudorandomness and reproducibility, and bf16 rounding
   preserves both.
5. **The coverage that IS removed is coverage of a state that becomes
   unrepresentable.** After this change no weight in this tower can hold a value
   that is not bf16-representable, in the fixture or from the checkpoint — the
   artifact is 1436-for-1436 BF16 (§5). Testing behaviour on f32-only weight
   values would be testing an input the type system no longer admits.

**The fixture does not degenerate under the rounding.** Measured, not asserted:

| tensor | n | distinct | zeros | min abs |
|---|---:|---:|---:|---:|
| `conv1` | 768 | 495 | 0 | 3.929e-04 |
| `ln_pre_w` | 32 | 29 | 0 | 7.031e-01 |
| `blk0.ln_1_w` | 32 | 29 | 0 | 7.070e-01 |
| `blk0.qkv_w` | 3072 | 1003 | 0 | 4.321e-06 |
| `blk0.fc_w` | 1536 | 726 | 0 | 1.168e-05 |
| `ad_fc` | 2048 | 819 | 0 | 9.358e-06 |

No value rounds to zero and none reaches the denormal range. The repeated values
are the pigeonhole of an 8-bit significand over a bounded uniform range, not a
collapse: a layout defect permutes a whole tensor and moves the output by O(1),
which the `1e-6` bound sees regardless of how many individual values coincide.

### 4.3 The regeneration is itself gated — the diff must have a predicted shape

This is what makes the regenerated golden falsifiable. Of the seventeen arrays
in `muse_glimmer_vision_goldens.inc`, twelve depend on no bf16-storage weight
and **must come back byte-identical**; five depend on them and must move by
exactly the amounts §3.2 measured. Generated both ways here and diffed:

| must be byte-identical (12) | must move (5) |
|---|---|
| `kPatchify0`, `kPatchify1` (pixels only) | `kLnPre0` |
| `kPosEmb0`, `kPosEmb1` (`pos_emb`, unrounded) | `kLnPre1` |
| `kRopeCos0`, `kRopeCos1`, `kRopeSin0`, `kRopeSin1` (weightless) | `kBlock0` |
| `kSparsePerm0`, `kSparsePerm1`, `kSparseSeqLens` (index-only) | `kTowerOut` |
| `kPixelShuffleRamp` (a fixed ramp) | `kAdapterOut` |

A thirteenth array moving, or one of the five not moving, means the generator
change reached something it should not have. That is a stop condition (§9).

**One caveat the implementing wave must expect, found here.** Re-running the
COMMITTED generator on `torch 2.11.0+cu130` does not reproduce the committed
`kAdapterOut` exactly: 13 of its 208 values differ, `rel_l2=4.627e-08`,
`max_abs=1.490e-08`. The other sixteen arrays reproduce byte-for-byte. That is a
last-ulp difference between the torch that generated the committed file and the
torch on this host, twenty times inside the f32 arm's own `1e-6` bound, so it
threatens nothing — but a regenerated `kAdapterOut` will carry it in addition to
the intended change, and a reviewer must not read it as a mistake. **The
generator is not bit-reproducible across torch versions**, which is a fact about
this fixture worth recording whether or not this row lands. The §6.2 gate is
therefore stated as a tolerance on the five and byte-identity on the twelve.

## 6. Gates — declared before any number exists

Correctness first. The memory axis is the reason the row exists, but it is not
accepted until the golden argument is green, because a token or tolerance gate
cannot see a dtype that is too wide and a re-recorded golden cannot see anything
at all.

### 6.1 The memory gate

**Not re-declared here.** Both halves are the parent spec's §6.1, applied with
`--model-kind muse-glimmer`:

1. **Default arm:** `peak_rss(pre-fix) - peak_rss(post-fix) >= 3,459,322,368 B`
   (0.90 x the on-disk tower, confirmed in §5 above).
2. **`--language-model-only` control arm:** `peak_rss` unchanged **within 2%**.
   That arm loads no tower, so this row cannot move it. If it moves, the
   measurement is about something other than the tower and the axis is VOID, not
   MET.

Instrument: `scripts/mm/tower_skip_rss.sh --model-kind muse-glimmer`, reading the
per-leg `peak RSS default` / `peak RSS lang-model-only` keys. Muse Glimmer's
workload is `completion`, not `load-only` (`tower_skip_rss.sh:431`, in
`declare_model`'s `muse-glimmer` arm at `:428-432`).

An outcome below either half is a FAILING axis, recorded as failing and left
open. The parent's §6.1 deviation is instructive and must not be repeated: run
both arms on ONE host, at this commit and at its parent. The Qwen3-VL result was
rescued by its control arm across a host change; do not spend that margin twice.

### 6.2 The golden gate — the numbers this row is really judged on

**A. The regeneration diff has the shape §4.3 predicts.** Against the committed
`muse_glimmer_vision_goldens.inc`:

- the twelve weight-independent arrays are **byte-identical**;
- the five weight-dependent arrays each differ in **every** element, at
  `rel_l2` of **2.220e-03** (`kLnPre0`), **2.164e-03** (`kLnPre1`),
  **2.193e-03** (`kBlock0`), **2.892e-03** (`kTowerOut`), **3.462e-03**
  (`kAdapterOut`), each to within 1% of the stated value;
- `kAdapterOut` may additionally carry up to **5e-08** of torch-version drift
  (§4.3), and nothing else may.

A different shape means the generator change reached something it should not
have. This is the assertion the whole row turns on, and it is stated before the
implementing wave regenerates anything.

**B. The f32 arm returns to its residual.** All five assertions at
`test_muse_glimmer_vision.cpp:316,320,325,330,337` green at their UNCHANGED
`1e-6` bound, and the reported `rel_l2` values **at or below 1e-6** — that is,
back in the 1.0-3.0e-07 band the record states for the pre-change tree, not
merely under the bound. A reading between 1e-7 and 1e-6 is a PASS that must be
reported and explained, because §4.2's construction argument predicts no change
at all.

**C. The bf16 arm does not get looser.** Its structural `2e-2` bound
(`:354`, `:406`) is UNCHANGED. Additionally, and declared here:

- **hard ceiling 8.843e-03.** The C++ bf16 output is unchanged by this row
  (§3.3), and the golden moves by 2.892e-03 on `kTowerOut` (§3.2), so by the
  triangle inequality no correct implementation can read above
  `5.951e-03 + 2.892e-03`. Both terms are relative to the committed golden's
  norm and the new golden's differs from it by at most the shift itself, under
  0.3%, so read the ceiling as `8.843e-03` with that 0.3% of slack rather than
  as a hard third digit. A reading above it means the storage change moved the
  bf16 path too, and is a stop condition (§9).
- **predicted value ~5.201e-03.** The old reading decomposes as
  weight-rounding plus activation-rounding, and this row removes the first term
  from the comparison, so `sqrt(5.951e-03^2 - 2.892e-03^2)`. Report the measured
  value against this prediction. A decrease is the expected outcome and is
  CORRECT, not a loosening: the golden and the implementation now agree about the
  weights, so the residual is the activation envelope alone.
