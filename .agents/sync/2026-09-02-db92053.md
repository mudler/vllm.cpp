## 1. Why this target and not the head

### 7.3 The version string, and a tag that would have corrupted it

Job B measured the pair the `parity-pin` block wants, from `cd /` so it read the
installed package rather than a source tree:

```console
SCM_VERSION   = 0.26.1rc1.dev958+gdb92053e9
VLLM_VERSION  = 0.26.1rc1.dev958+gdb92053e9        # vllm.__version__
DIST_VERSION  = 0.26.1rc1.dev958+gdb92053e9.precompiled
```

It has the shape the block requires: a `+g<sha>` segment that prefixes the
target commit, so `assert_oracle_commit` is satisfiable, and a distribution
string carrying the `.precompiled` suffix the runtime string lacks, which is
the same relationship the pin's own pair has. **These values are recorded here and are
NOT written into the `parity-pin` block**, because the pin does not move. A
future cycle re-measures rather than transcribing them, for the reason the next
paragraph gives.

**The reference checkout would have produced a different and wrong string.**

```console
$ git -C ${VLLM_SOURCE} describe --tags db92053e97
v0.27.2rc0-265-gdb92053e97
# job B, from a clone taken fresh from GitHub:
GIT_DESCRIBE=v0.26.1rc0-958-gdb92053e97
```

They disagree because `v0.27.2rc0` exists only in the local checkout.
`ls-remote --tags origin` lists 184 tags, `show-ref --tags` lists 177 locally,
and `comm -23` between them returns exactly one name: `v0.27.2rc0`, pointing at
`7f7a32cfec`. It is reachable from the target and nearer than `v0.26.1rc0`, so
it wins `describe`. The two `describe` outputs are measured; what a build from
the local checkout would then report is derived from them and was not run,
because nothing should build an oracle from a checkout with a tag upstream
deleted.

`assert_oracle_commit` would not have caught it. It extracts the `+g<sha>`
segment and requires it to prefix `vllm_commit`, which is true of both strings.
This is [#1185](https://github.com/mudler/vllm.cpp/issues/1185)'s class again,
a checkout property silently rewriting the version prefix, and it is the
concrete reason the guide says a pin advance is taken from a measured
`vllm.__version__` and never transcribed.
[#2591](https://github.com/mudler/vllm.cpp/issues/2591) tracks the repair,
`git fetch --prune --prune-tags origin`, which belongs on the developer's
machine rather than in a diff.
