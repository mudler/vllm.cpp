## 1. The question, and the answer

[`2026-09-01-cdefd9d.md`](2026-09-01-cdefd9d.md) §9.2 measured that upstream's
head does not install on this fleet, and named the cause: `2d7f42b4f3`
vllm#52801 promoted `instanttensor` from `requirements/test/*`, where it carries
`platform_machine == "x86_64"`, into `requirements/cuda.txt` with no platform
marker, and every fleet device is aarch64. From that measurement the PINPORT
wave concluded that **no revision carrying `qwen4_exp` can be pinned on this
fleet**, because `2d7f42b4f3` (2026-08-19) is an ancestor of `e126687a9a`
(2026-08-31), the commit that registers the model.

The PINWINDOW wave ([#2589](https://github.com/mudler/vllm.cpp/issues/2589))
then measured, as a trailing probe in its own job, that `instanttensor 0.1.9`
**does** build from source on aarch64 once Python headers are present, and was
explicit that this did not overturn the conclusion:

```console

APTDEV_RC=0            # apt-get install -y python3-dev
ITENSOR_DEV_RC=0       # Successfully installed instanttensor-0.1.9
```

Nobody had re-run the runtime-requirements install at a `qwen4_exp`-carrying
revision with the header package present, so the repair was a hypothesis and the
head's `RUNDEPS_RC=1` stood as the measurement. This wave runs it at the earliest
revision that serves the row.

**The answer is that the target installs, builds and imports, and that the model
is registered in what was installed.**


Two of those rcs do not mean what the line makes them look like. `EXT_RC=1` is
expected and is not a target defect; §5.5 says why. **`APTDEV_RC=0` here confirms
nothing about the worker image**, because job B reused job A's container and
found the headers already installed; job A is the job that measured `absent` then
`present`, and §5's table says so. **The run half
is still not measured**, so this target's `gateable` stays `no` and the pin does
not move. What is now wrong is the narrower claim: the head of upstream was not
