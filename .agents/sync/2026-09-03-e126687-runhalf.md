level 2 of the three levels [the spec](../specs/upstream-sync-headpin-runhalf.md)
§2.1 sets out: a real checkpoint generating tokens greedily through vLLM's
normal path, on vLLM's own default attention backend, in both the eager and the

## 4. `EXT_PRESENT`, measured by executing a kernel rather than by a name

**`EXT_RC=1` was reported once in this wave against a wheel that carried seven
compiled extensions.** The probe asked for `vllm._C`, which is the name every
prior HEADPIN job asked for and which a CUDA build of this revision does not
produce at all. It was not renamed: `CMakeLists.txt:367` guards the legacy `_C`
extension with `if(VLLM_GPU_LANG STREQUAL "HIP")` under the comment
`Legacy _C extension (ROCm only -- CUDA ops migrated to _C_stable_libtorch)`,
so `_C` still exists on ROCm and CPU and the CUDA ops moved out from under it. A missing module is not a missing
extension, and this is the failure mode the row keeps paying for.

## 6. The stretch leg: `qwen4_exp` does NOT run on `thor:gpu0`

`Q4EXP_RC=1`. This is the one result here that is about the target's own model,
and it is reported with every qualifier it needs.

The configuration is the model's **published** `config.json` from
`Qwen/Qwen3.8-Flash-Next`, reduced in **depth and count only** — 48 layers to 4
keeping one `full_attention` among three `linear_attention`, 512 experts to 8,
`ngram_vocab_size_base` 20,000,000 to 20,000 — with `load_format="dummy"`, so
the weights are random. Width was left alone: an earlier attempt halved
`head_dim` and tripped
`assert sum(self.mrope_section) == rotary_dim // 2` in `mrope.py:289`, which is
this wave's instrument and not a finding.

The model built, allocated, and ran a forward pass into the QSA indexer, where a
compiled kernel refused to launch:

```console
File ".../vllm/models/qwen4_exp/nvidia/indexer_qsa.py", line 343, in forward
    return qsa_select_paged_tokens(
File ".../vllm/models/qwen4_exp/nvidia/ops/qsa.py", line 799, in qsa_select_paged_tokens
    topk_op(logits, visible_blocks, blocks, topk_workspace, block_topk, columns)
RuntimeError: launch_cooperative_cluster, csrc/libtorch_stable/cooperative_topk.cu:46,
  cooperative_topk launch failed: a kernel launch error has occurred due to cluster misconfiguration
```

The kernel exists for this device: `CMakeLists.txt` lists `11.0f` in
`COOPERATIVE_TOPK_ARCHS`, and it was compiled. What fails is the **cluster
launch**. `cooperative_topk.cu` launches `clusterDim = {1, CS, 1}` where `CS` is
a compile-time template parameter of 4, 8 or 16, and it sets
`cudaFuncAttributeNonPortableClusterSizeAllowed` for `CS > 8`, which is upstream
saying in its own code that the large size is not portable. The arm is selected
by `const bool supports_cluster16 = get_device_prop()->major >= 10;` — a
compute-capability major used as a proxy for a cluster-size capability, which
admits Thor's 11.0.

**The obvious hypothesis, that the 16-CTA arm is the whole story, was tested and
NOT confirmed.** A second leg with a larger batch, intended to select the 8-CTA
arm, failed with the identical error. That A/B is **inconclusive rather than
negative**, because `num_rows` at that call site is the number of scoring rows
rather than the request batch, so the knob did not move the variable it was
chosen to move. What stands is narrower and is enough:

- `qwen4_exp`'s QSA indexer does not run on `thor:gpu0` at this revision, under
  every configuration tried.
- The cause is localised to a thread-block cluster launch at
  `csrc/libtorch_stable/cooperative_topk.cu:46`, and the cluster size is a
  compile-time constant that no configuration of this wave's could have changed.
- **Which cluster size was attempted is not established**, and Thor's actual
  maximum cluster size was not queried. Both need a lease this wave did not
  spend.

This is a genuine upstream portability gap on NVIDIA Thor, filed as
[#2626](https://github.com/mudler/vllm.cpp/issues/2626) and owned by
`MODEL-MM-QWEN4-EXP`, which lists it under `## Owed` in
[`../specs/qwen4-exp-flash-next.md`](../specs/qwen4-exp-flash-next.md). It
outlives this sync wave, so it is deliberately NOT owned by
`UPSTREAM-SYNC-HEADPIN`, which closes with it. It does not bear on §1 under the permissive reading of AGENTS.md's
sentence, on which "runs the model" is satisfied by any model; it plainly does
bear on §1 under a strict reading, on which the model an oracle must run is the
model the candidate is wanted for. **This report takes the permissive reading
and does not claim it is settled.** Either way level 1 was out of reach for the
weights, and either way the pin does not move.

## 7. What this establishes, and what it does not

**Establishes.** `e126687a9a` builds from source on aarch64/sm_110, ships a
working extension, and serves a model to greedy tokens on vLLM's default
backend, eager and compiled. That is the run half, and it is the condition

**Does not establish, and the pin does not move.**

- **C1. The 290-entry PORT-NOW queue for `5559679229..e126687a9a` is unworked.**
  This wave adds nothing to it and removes nothing from it (#2611).
- **C2. Nothing here is a correctness gate.** Six prompts at 16 tokens against a

  happened to agree. The declared token-exact gate a pin advance owes is
  unmeasured.
