## 3. `nvidia-cutlass-dsl` is NOT discharged. It is narrowed, and it is owed

**A fresh review of [#2783](https://github.com/mudler/vllm.cpp/pull/2783)
falsified this section's original claim, and the falsified sentence is quoted
here rather than deleted.** It read: *"It is not on any executed path this fleet
can take."* **That is wrong.** There is a fourth path, it is not
family-100 gated, and it compiles CuteDSL at engine start on GB10.

### 3.1 The path the first pass missed

`vllm/model_executor/warmup/kernel_warmup.py:125-126` @ `5559679229`:

```python
    if current_platform.has_device_capability(90):
        _warmup_ll_bf16_router_gemm()
```

**`has_device_capability` is `>=`, not a family test.**
`vllm/platforms/interface.py:447-454` returns
`current_capability.to_int() >= capability`, so `sm_121` passes `90`. The three
paths §3.2 enumerates all use `is_device_capability_family`
(`interface.py:481-493`), which is `//10` equality and excludes `sm_121`. Reading
one predicate and generalising to the other is exactly how the original sentence
came to be written.

The callee gates on nothing else that could save it.
`kernel_warmup.py:57-72` calls `is_ll_bf16_gemm_available()` and returns early
only if that is false; `kernels/linear/cute_dsl/ll_bf16.py:19-31` implements it
as a bare `import cutlass; import cutlass.cute` inside a `try/except
ImportError`, **with no capability check at all**. It then calls
`ll_bf16_gemm_kernel.warmup(...)`, which loops into `compile(...)`
(`ll_bf16.py:188-206`) with **no `try/except`**. That is real CuteDSL
compilation.

`kernel_warmup(worker)` is called **unconditionally** from
`vllm/v1/worker/gpu_worker.py:704`, before CUDA-graph capture, and is not
conditioned on the model.

**This wave's own evidence closes the loop.**
`.agents/benchmark-record.md:12979` records the staged GB10 stack as
"cutlass-dsl 4.6.0 ... installs+imports on GB10", so `is_available()` is `True`
there and the compile ran on the host both affected gates were measured on.

### 3.2 What is still true, and it is the narrower ground

The **steady-state compute path** is family-100 gated and does not fire on GB10.
`vllm/model_executor/layers/fused_moe/router/gate_linear.py:59-62` @
`5559679229`:

```python
        is_hopper = current_platform.is_device_capability((9, 0))
        is_blackwell = current_platform.is_device_capability_family(100)
        can_use_specialized_kernels = (
            current_platform.is_cuda() and (is_hopper or is_blackwell) and not bias
        )
```

`is_device_capability` is EXACT equality (`interface.py:470-476`), so `sm_121` is
not Hopper, and `121 // 10 != 10`, so it is not the Blackwell family either.
`can_use_specialized_kernels` is therefore `False`, `allow_ll_bf16_gemm` stays
`False` (`:127-137`), and the Tier-1 dispatch at `:171-177` never runs.

The other three paths stand as originally written:

1. **NVFP4 linear.** `FlashInferCuteDslNvFp4LinearKernel.is_supported` returns
   `False, "FlashInfer cutedsl requires sm_10x"` unless
   `is_device_capability_family(100)`
   (`kernels/linear/nvfp4/flashinfer.py:35-42`). First in
   `_POSSIBLE_NVFP4_KERNELS` (`kernels/linear/__init__.py:448`), skipped here,
   which is why §2.2's selection lands where it does.
2. **GDN prefill.** `_resolve_gdn_prefill_backend` sets `supports_cutedsl` only
   inside the `is_device_capability_family(100) and head_k_dim == 128 and
   get_cuda_runtime_major() >= 13` branch, and its `cutedsl` return additionally
   requires the backend to be explicitly requested, never `auto`
   (`layers/mamba/gdn/qwen_gdn_linear_attn.py:112-133`; docstring `:97-100`,
   "opt-in only"). On a family-120 host it returns `triton`.
3. **FA4.** The `import cutlass` calls at
   `v1/attention/backends/flash_attn.py:1401-1403` and `:1489-1490` @
   `5559679229` are function-local on the FA4 path; the recorded runs selected
   FA2 (`docs/bench-evidence/qwen35-4b-pinned-oracle-20260728.md:35-36`, and
   `2026-09-03-e126687-runhalf.md` §2 at the target).

### 3.3 The disposition, restated honestly

**`nvidia-cutlass-dsl` cannot move the steady-state math of either affected
gate**, because §3.2's dispatch never fires on `sm_121`. That is the only part
of the original discharge that survives.

**It can do two things the original section denied, and both are owed.**

- **A `4.6.0` to `4.6.2` change that breaks the warmup compile aborts engine

- **The compile is inside vLLM's startup window, and this project publishes a

  (`kernel_warmup.py:47-55`) sits inside that 182.41 s. **This report does not
  claim a magnitude and did not measure one**; it names the row as one the next
  wave must evaluate rather than one it has excluded.

`docs/bench-evidence/qwen35-4b-pinned-oracle-20260728.md:32` and

target's requirement, and no recorded number was taken under a `transformers`

**What the floor move does not cover, said plainly rather than hidden.** A
rebuild of the oracle environment at the target resolves the open floor to
whatever is newest that day: `2026-09-02-e126687.md` §5.2 measured
`transformers 5.16.1` there. That is a real move of the installed version. Its
cause is `pip` resolving an open bound on a rebuild, and it would happen
identically had the floor not moved at all, so it is not this denominator. It
belongs to the pin advance's own golden-drift re-validation, which
`.agents/specs/pin-advance.md` §3 already treats as such and which
`2026-07-26`'s advance discharged by re-capture rather than by argument.

**`thor:gpu0` would not serve this even when it is free, and that is the point
rather than the scheduling.** Both affected gates are **GB10 `sm_121a`** gates.
Thor is `sm_110`. Every fact in §2.2 that puts FlashInfer on the denominator's

the DFlash backend selection in §2.6 is recorded as "`flashinfer-native` fp8-KV

`docs/benchmarks/vllm-online-serving.md:66-67`, `:106-107` or
`docs/benchmarks/speculative-decoding.md:6`. Running one there and calling it a
step-6 baseline would be exactly the substitution

**The harness would refuse the run anyway, and that is a finding rather than an
excuse.** `FLASHINFER_VERSION` is read from the `parity-pin` block
(`serve_low_common.py:109`) and asserted at `online_gate.py:3552-3560` and again
at `:3714-3720`.

**The circularity is broader than the FlashInfer move, and this is the general
statement of it.** `online_gate.py:3529-3540` refuses on
`VLLM_DISTRIBUTION_VERSION` and `VLLM_ORACLE_VERSION` **before** reaching the
FlashInfer gate, and `assert_oracle_commit` follows at `:3542`. All three come
out of the same `parity-pin` block. So **the block must be edited before ANY pin
advance can be measured through this harness**, not only before this FlashInfer
move. The dependency is structural.

It is also new rather than a shape somebody has already navigated. The harness
historically carried its own constants and lagged the record
(`serve_low_common.py:30-38` records the drift), and #520 is what made it read
the record instead. That repair is what created the circularity, so there is no
precedent to copy. At the target FlashInfer is `0.6.18`
(`2026-09-02-e126687.md` §3 and §5.2, `PIPLIST flashinfer-python 0.6.18`), so
`scripts/dgx-online-serving.sh` refuses at its `record-oracle` step
(`:305`). The `cutlass_source_tree` contract (§2.3) fails the same way, because
the tree it fingerprints lives inside the FlashInfer package that just moved.

### 6.1 The refusal is measured, not read

The paragraph above would otherwise be a code read, and it is the claim that
decides whether the next wave's job can run at all, so it was executed.
`.agents/scripts/step6-flashinfer-refusal-probe.py` (sha256
`044fa60225ffb876affa2c21da94fd14f8226b6d3a85fd69cdb07cb4e0619d79`) builds the
same hermetic fixture tree `tests/tools/test_online_gate_client.py:1990-2078`
builds, then calls the committed `record_oracle_manifest` twice, changing only
the FlashInfer version. No GPU, no network, no oracle. It takes the repo root
from `argv[1]`, defaulting to its own location's grandparent, and aborts if that
is not a checkout — an earlier version hardcoded an absolute worktree path,
which AGENTS.md requires be removed when the work merges and which a later wave
reusing the directory name would have made silently read a different tree.

```console

PIN_FLASHINFER=0.6.15.post1  TARGET_FLASHINFER=0.6.18
LEG CONTROL(pin):    RAN, rc=1, PASSED_FLASHINFER_THEN_oracle client and Python are not from the sa
LEG TARGET(0.6.18):  RAN, rc=1, REFUSED_AT_FLASHINFER: FlashInfer oracle dependency drift:
                     metadata='0.6.18', runtime='0.6.18', expected='0.6.15.post1'

```

**Both legs are refusals, and they are refusals at different checks.** The
control dies at `online_gate.py:3586`, which is strictly after the FlashInfer
gate at `:3552-3560`, so it reached that line only by passing the gate; the
fixture is not a complete oracle and was never meant to be. The target dies at
the gate itself, naming the two versions. The probe classifies by which check
refused rather than by the exit status, because both exit non-zero and a
verdict keyed on the status alone would have read "no difference".

**Its first version printed `INCONCLUSIVE` and that was correct behaviour.**
The verdict was originally keyed on `control_rc == 0`, which the fixture cannot
produce, so the probe said it had not discriminated instead of reporting the
target's refusal as a finding. It is recorded here because an instrument whose
failure looks like a result is this row's recurring trap, and this is the one
place in this wave where the instrument had the chance to fall into it.

So step 6's re-measurement and the harness's own fail-closed pin assertion are
in tension:

- Editing the `parity-pin` block first makes the measurement possible, but that
  edit **is** the pin advance, which step 6 is a precondition of. It is also
  outside this wave's authority and the spec's stop conditions.
- Measuring outside the committed harness produces exactly the kind of number
  this project refuses. `.agents/benchmark-record.md` and
  `docs/benchmarks/how-we-measure.md:56-57` are explicit that a
  stale-denominator or unasserted number is not published as binding, and #520
  exists because an oracle that "runs, looks healthy, and is not the one the
  record names" once produced 17 days of refused measurements.

Nothing in `.agents/upstream-sync.md` says which moves first. That is
`NEEDS_DECISION`, it is carried in §7, and this wave did not resolve it by
loosening an assertion.
