### 2.3 A fifth and a sixth false-zero mechanism, both found in this wave

The brief carried the four the earlier tranches paid for. Two more appeared here,
and the first one bit the operator, not a reader.

**Fifth: `grep` in this shell is a function wrapping `ugrep`, not GNU grep, and
without `-r` it skips a directory argument in complete silence.**

```console
$ grep -n  'GetFreedMmHashes' src include   # nothing, empty stderr, rc=1
$ grep -rn 'GetFreedMmHashes' src include   # 4 hits, rc=0
$ /usr/bin/grep -n 'GetFreedMmHashes' src include
/usr/bin/grep: src: Is a directory
/usr/bin/grep: include: Is a directory      # rc=2
```

This is worse than the four already recorded, because the usual defence fails.
GNU grep answers **rc 2** — "your probe was malformed" — and prints a diagnostic.
`ugrep` answers **rc 1**, which is the canonical "no match found". A
well-formed-looking probe returns the canonical absence answer leaving no trace.
It was caught here only because the same concept was greppable under a second
spelling, which is exactly what §2.4's two-spellings rule is for. All six readers
were sent the mechanism mid-wave and re-ran their zeros; every zero recorded
below carries `-r`.

**Sixth: `-F` does not do alternation either.** Two readers independently wrote
`grep -rniF "a\|b\|c"`, which under `-F` searches for one long literal string
containing backslashes and pipes, and returns zero. The brief's own advice to
"prefer `grep -rF` fixed strings" invites this, so it now carries a clause: **one
needle per call.** This is distinct from the malformed-ERE mechanism already
recorded, which bites under `-E`.

A seventh was also met and is a repeat of a known zsh trap rather than a new
mechanism: an unquoted `$scope` variable holding several paths does not
word-split in zsh, so the probe searched one nonexistent directory. Its reader
caught it because the **positive controls went to zero too** — which is the whole
argument for running them.

### 4.2 Four of the eleven are worse than a missing forward-port

- **`[187]`** is a silent out-of-bounds write, not a missing feature. An
  over-long row writes into the next row of a `std::vector<int32_t>`, or past the
  end on the last row. The pressure is real — `MambaManager` allocates
  `cdiv(num_tokens, block_size) + num_speculative_blocks`
  (`single_type_kv_cache_manager.cpp:798`) with a live non-zero producer
  (`qwen3_5_common.cpp:90`), against a row width of `cdiv(max_model_len, bs)`.
  What keeps it in bounds today is arithmetic luck: the width is rounded up to a
  multiple of `128 / block_size`, granting up to 7 blocks of slack at
  `block_size == 16`. Nothing was run, so whether a shipped configuration crosses
  it is undetermined; a guard is warranted either way.
- **`[197]`** is worse in this tree than the bug upstream fixed. Upstream's
  terminated matcher merely returned `False`; here the unguarded scheduler caller
  turns that into `RequestStatus::kFinishedError` (`scheduler.cpp:1286`), so a

  true for a lazy grammar awaiting its trigger, so an unconditional early-out
  would silently disable constraint enforcement for every structural-tag grammar.
- **`[178]`** is a live HTTP 500 on a registered production route, reachable by

- **A false ALREADY_SATISFIED is more dangerous than a false REAL_GAP.** A gap

  the same false zero as an unmatched grep. Check for the terminal summary line
  first, then read the markers.
