### 2.3 An eighth false-zero mechanism, and it is content-dependent

The brief carried seven. An eighth appeared here, and it is the worst of the set
because the same probe form works on every other input.

**`echo "$var"` in zsh expands backslash escapes, and one NUL byte anywhere in
the stream makes this shell's `grep` return the canonical no-match answer for the
WHOLE stream, silently, at rc 1.**

```console
$ tgt=$(git show e126687a9a:vllm/v1/structured_output/backend_xgrammar.py)
$ echo   "$tgt" | grep -xF -c '            return True'   # (nothing)   rc=1
$ printf '%s\n' "$tgt" | grep -xF -c '            return True'   # 6     rc=0
$ echo   "$tgt" | /usr/bin/grep -xF -c '            return True'  # 6    rc=0
$ echo "$tgt" | wc -c            # 14376
$ echo "$tgt" | tr -d '\0' | wc -c   # 14375   -- exactly one NUL
```

The file contains the four-character literal `\x00` (inside upstream's own
NUL-byte guard). `echo` in zsh turns it into a real NUL byte. The `grep` shell
function passes `-I`, "ignore binary files", so `ugrep` classifies the entire
stream as binary and reports no match. GNU grep on the identical stream returns
six.

This is mechanism 5's shape — rc 1, the canonical absence answer, no diagnostic —
but triggered by **content** rather than by a malformed probe. It cost this wave
a survival scan that read four entries as 0 percent surviving to the target, of
which two were plain false. **The rule that follows: pipe with `printf '%s\n'`,
or better, write to a file and let `grep` read the file.** The control that
catches it is the same needle against the same content from a file.

Mechanism 7, the zsh non-splitting of an unquoted path variable, also fired
twice — once emptying a `git show -- $FILES` pathspec to zero hits, once making
`set -- $pair` bind the whole string to `$1` so four unrelated entries were
reported against `HEAD`'s files. Both were caught by a control, and the fix in
zsh is `${=var}`.

**Read the report text, and know exactly what the status can and cannot tell
you.** `grep -nE 'gate\(s\) failed'` returns **no match**; `grep -nE 'NOT a green'`
returns **one** line, and it is the skip notice — "a skipped gate reported nothing
about this tree" — not a failure.

The rule is narrower than "never trust the exit code", and the narrow version is
the useful one:

- **A failure IS reliably in the exit status.** `scripts/agent-preflight.sh:679-684`
  prints `N gate(s) failed` and then `exit 1`, unconditionally.
- **A SKIP is NOT.** With skips and no failures the script falls through to
  `exit 0` while printing `NOT a green preflight`. The comment at `:702` gives the
  reason: exiting 1 for a skip would merge "a gate did not run" into "a gate ran
  and the tree is wrong", which are different facts. `--fail-on-skip` is the
  opt-in for a caller that reads only the status.

So the text must be read for **skips**; for failures the status suffices.
