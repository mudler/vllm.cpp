### 2.2 C1c: UNANSWERED — this workload cannot exercise it, and engine start was not aborted

C1c asks two things. **This log answers neither.** What it establishes is one
narrower negative: engine start was not aborted on GB10. An earlier version of
this section called that "NARROWED", which is one notch too generous, because a
warmup body that is never reached cannot narrow a question about what the warmup
does.

**Question 1, whether the `4.6.2` warmup compile succeeds on GB10 at all.** The
`kernel_warmup` block ran on a device at compute capability 12.1 and did not
fault:

```
INFO 09-04 12:44:13 [kernel_warmup.py:124] JIT kernel warmup starting.
INFO 09-04 12:44:13 [kernel_warmup.py:134] JIT kernel warmup finished in 0.00s.
```

and the engine reached the model and produced tokens after it. The
`has_device_capability(90)` gate #2818 names at `kernel_warmup.py:125-126` sits
between those two lines; the identification is by module and by adjacency in the
emitted line numbers, and this session did not read the pinned vLLM source to
confirm it, because doing so needs the tree the leased build had.

**This is not a weak instance of the question. It is consistent with the question
never being asked.** The model is `facebook/opt-125m`: dense, unquantized, bf16,
`enforce_eager=True`, single GPU. The engine's own config line shows
`enable_cutedsl_warmup=True`, so the knob was on — and `0.00s` between the two
lines, on a model that reaches no MoE router GEMM, is what a guarded `compile(…)`
that is never reached looks like. The `Warming up ll_bf16 router GEMM kernels.`
line §7 asks for **did not appear**: zero for `ll_bf16`, zero for `router GEMM`,
and zero for the wrap-immune substring `Warming up`, raw and
whitespace-stripped, against positive controls of four `kernel_warmup` and six
`autotun` hits counted the same way in the same file, so the search shape is not
the reason for the zeros. (`router_gemm` matches once, inside the config dump as
`enable_bf16x3_router_gemm=False`, which is a knob name and not a warmup trace.)

So the only supported reading of `0.00 s` is **engine start was not aborted**. It
is not evidence that the `4.6.2` compile path was entered, and it is not evidence
about what that path costs on the NVFP4 checkpoints the startup row measures. Both
of C1c's questions stay open, and a lease that wants to answer them needs a model
whose router GEMM the warmup actually reaches.

**Question 2, what fraction of the oracle's 182.41 s startup the CuteDSL warmup
is, is untouched.** Nothing here measures a startup ratio, and nothing here can:
182.41 s is the **27B startup row's** figure, from a different model on a
different checkpoint, and this job never ran that row. An earlier version of this
paragraph divided this model's autotune time by that row's denominator, which is
a denominator swap and not a ratio.

One adjacent observation is worth carrying to whoever takes the lease, and it is
a candidate rather than a result: **FlashInfer autotune took ~58.6 s** on this
trivial model (`12:44:13,914` to `12:45:12,481`, log L177 to L179) and saved
**0 configs**. Against this model's OWN startup, `init engine (profile, create kv
cache, warmup model) took 262.64 s` at log L184, that is **22.3%** — just over a
fifth of the budget from a function that is not CuteDSL warmup. Whether that
fraction holds for the 27B row is exactly what the row has to measure; the point
that
survives is that its decomposition should measure autotune and CuteDSL warmup
separately rather than attribute the whole to one.
