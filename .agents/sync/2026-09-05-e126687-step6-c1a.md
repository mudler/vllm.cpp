### 5.1 What the version read is for, and what it must NOT be used for

`importlib.metadata.version("vllm")` is read from `cd /`, together with the
FlashInfer and runtime versions, and recorded verbatim. **If any of them differs
from the ` ```parity-pin ` block, the run stops and the difference is reported.**
The block is not edited to make a run pass. That is the #520 failure, and this
tree spent 17 days refusing the oracle its own record required rather than commit
it.

### 5.2 CUTLASS comes from the ORACLE's flashinfer, not from our own tree

`.agents/benchmark-record.md:1932-1934` pins the online-serving build to
`-DVLLM_CPP_CUTLASS_DIR=<oracle venv>/lib/python3.12/site-packages/flashinfer/data/cutlass`
-- "the oracle's own cutlass tree, not `$HOME/cutlass-4.5.0`". That is what makes
it the same input on both sides of the ratio, and it is also why FlashInfer's move
to `0.6.18` reaches our arm and not only the denominator. The dispatched job uses
that path and no other.

The job pre-builds `server` and `test_qwen36_paged_engine` at `-j 4` before
invoking the driver, so the driver's own `build_jobs=$(nproc)` finds nothing to do.
AGENTS.md records that unconstrained parallelism has OOM-rebooted this box.

### R3. The grid did NOT run. Blocker one: THE LEASE CANNOT PIN THE CLOCKS

```console
+ nvidia-smi -lgc 2190
The current user does not have permission to change clocks for GPU 0000000F:01:00.0.
Terminating early due to previous errors.
+ echo LGC_RC=4
LGC_RC=4
```

`nvidia-smi -pm 1` succeeded (`PM_RC=0`); only the clock lock was refused. The
release at the end failed the same way.

**This is structural and it is not specific to this wave.** §7 C1a of the
predecessor requires "clocks pinned at 2184 MHz", and `BENCH-ASSERT-CLOCK-STATE`
(#543) exists because every figure taken before clock assertion was repriced when
it arrived -- `marlin::Marlin` moved 9.65% on a median that read 2470 against a
requested 2190. If a leased container cannot set `-lgc`, then **no benchmark run
from inside an `rc` lease on this box can satisfy the recipe it is measured
against**, and every such number is unclock-attributed by construction.

The reading taken immediately after the failure is
`clocks.current.graphics 208 MHz` against `clocks.applications.graphics 2418 MHz`.
208 MHz is an idle clock and NOT evidence of throttling under load -- no load was
running at that instant -- so it is recorded as a reading, not as a finding.

What is owed is the capability, not a workaround: either the lease grants the
privilege `-lgc` needs, or the recipe's clock requirement is unsatisfiable here
and every axis that depends on it stays PENDING. Choosing to measure without
pinned clocks is the third option and it is the one this project has already
paid for.

The causal order matters and is easy to invert when reading the log bottom-up:
the `--execute` failure is a CONSEQUENCE of the `--dry-run` refusal, not a second
independent defect. The dry-run ran against an evidence directory that
`--prepare-corpus` had already populated with the c1..c32 `jsonl` files, and the
driver refuses to mix plan artifacts into a directory that already holds them.
That is the driver protecting a keyed record, and it is a sequencing error in the
job rather than a defect in the harness.
