The whole product surface differs by ONE hunk, and it is inert for this build:

    +if(TARGET test_bench_eos_chat_template AND TARGET vllm-bench)
    +  add_dependencies(test_bench_eos_chat_template vllm-bench)
    +endif()

This job configures with -DVLLM_CPP_BUILD_TESTS=OFF, so `test_bench_eos_chat_template`
is not a target and the block never fires. It also only orders two TEST targets;
it touches neither `vllm-cli` nor `libvllm.so`.

CONCLUSION. For this build configuration the two revisions produce the same
`vllm-cli` and the same `libvllm.so`. Re-pinning would rebuild an 88 MB bundle,
re-declare three constants and surrender the queue slot, to measure identical
bytes -- and main would move again during the rebuild. This repository has
already recorded that a full gate cannot finish between main moves.

What matters for #2933 is not that the pin is the LATEST head; it is that the
pin is ASSERTED and RECORDED, and that it is after the #2511 fix. c796fea41 is
3 days after that fix reached main as 27da7787e (2026-09-02 15:11 UTC).

So the pin stays, and this file is why. The published figure names c796fea41,
never "main", because "main" is not a reproducible identifier.
