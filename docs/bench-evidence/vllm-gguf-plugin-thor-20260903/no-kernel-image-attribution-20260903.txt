## 3. The counter-argument is refuted: those norms never run through _C.

The reason this attribution stayed open was that rms_norm_kernel sits in the
same arch class (block 15 above), and the forward plainly got past
post_attention_layernorm (qwen3_next.py:546) to reach the MLP at :554. If _C
were uniformly imageless AND the norms called it, the run would have died in
layer 0. It does not call it:

$ python3 ir_dispatch_probe.py --vllm <pinned vllm 5559679229>
qwen3_next.py: GemmaRMSNorm as Qwen3NextRMSNorm,
layernorm.py: weight = self.weight.float() + 1.0
vllm_c.py: exec'd rms_no_var_size, rms_add_no_var_size

x.dtype=torch.bfloat16  weight.dtype=torch.float32
vllm_c rms_norm            supports_args = False
vllm_c fused_add_rms_norm  supports_args = False

VERDICT: vllm_c is INADMISSIBLE for every Qwen3.5 norm; ir.op.dispatch falls
through to native, so no _C layernorm kernel is ever launched
PROBE_RC=0

Qwen3.5's norm is GemmaRMSNorm under an alias (qwen3_next.py:28), and
GemmaRMSNorm widens its weight to f32 before calling the IR op
(layernorm.py:157). vllm/kernels/vllm_c.py registers its rms_norm and
fused_add_rms_norm impls with supports_args predicates that require
weight.dtype == x.dtype, and vllm/ir/op.py:344-351 skips an impl whose
supports_args is False and takes the next entry of the priority list, which the
run's own logged kernel_config gives as ['vllm_c', 'native'].

The rotary kernel is in the same position, and it constrains the crashing
layer rather than being an input to the deduction: rotary_embedding_kernel is
sm_120-only too, so had this been one of Qwen3-Next's FULL-attention layers it
would have raised earlier. The crashing layer is therefore one of the
linear-attention layers, which carry no rotary embedding at all.

## CONCLUSION

Of the three launches in the window, two are in an object that carries an
sm_110 image and one is in an object that does not. The failing launch is
torch.ops._C.silu_and_mul, at qwen2_moe.py:114, between the two GGUF
projections. It is the FIRST vLLM _C kernel the forward reaches, which is why
the model loads and 40-odd layers' worth of norms and GDN attention run first.

This is a deduction from a complete enumeration of the window plus two offline
measurements, not a direct observation. CUDA_LAUNCH_BLOCKING=1 on the box, or a
cudaGetLastError after each launch, observes it directly and is still owed.
It predicts that dgx:gpu0 does NOT hit this wall, because that box is sm_121a
and the wheel's sm_120 SASS covers it -- and the wheel was built there and has
generated text there before (/workspace/oracle-vllm/README-WHEELS.md). rc job
7a45427e-ad86-4042-aeea-cdf8db535a54 is the run that reads that prediction out.

It also says the wall is NOT about GGUF, the plugin or this checkpoint: it is
the pinned vLLM wheel's own arch list, which is a build input.
