# Merged-GEMM consistency allowlist — model TUs that hand-roll a gated MLP
# epilogue (vt::SiluAndMul / vt::GeluAndMul) WITHOUT (yet) routing their gate-up
# through a shared merged-GEMM seam (the layers::MlpGateUpMethodBase method seam +
# its tuned quant arms, the vt::MergedGemmGroup descriptor, or the shared fused
# MoE op vt::MoeGateUpSwiGLUGrouped), accepted as a KNOWN, TRACKED state so
# scripts/check-fusion-consistency.py stays green while preventing a NEW
# unadopted hand-rolled-MLP model from landing silently.
#
# Each entry is a model-file stem (src/vllm/model_executor/models/<stem>.cpp) with
# a reason. Ranked fold order + the shared-op targets:
# .agents/specs/arch-fusion-fold-plan-2026-07-30.md (Tiers A1/C1/C2).
#
# Removing a stem here (after folding its gate-up onto the shared seam,
# byte-exact + token-exact/near-tie gated) is the enforcement gate closing — as
# happened for the 5 SwiGLU archs (Tier A1: olmo2/granite/stablelm/qwen3_dflash/
# deepseek_v2) and the Gemma family (Tier C1: gemma/gemma2/gemma3/gemma4), which
# now route through layers::UnquantizedMlpGateUp{,Gelu}Method and are NOT listed.
#
# NOTE: the seam already carries both activation arms (UnquantizedMlpGateUpMethod
# SwiGLU + UnquantizedMlpGateUpGeluMethod GeGLU) and the nvfp4 fused arm
# (GateUpFusedMarlinD) for free on quantized checkpoints — these models need only
# the fold (swap {gate;up;SiluAndMul/GeluAndMul} -> the method), no new kernel.
# Every listed model already ships a merged [2I,H] gate_up weight (no loader
# concat needed) — the gap is launch/epilogue granularity + seam routing only.

# --- KNOWN-DRIFT: seam exists, model has NOT adopted it (fix = fold, Tier A1/C1) ---
# commandr / glm4 / minicpm / minicpm3 / phi3 were HERE with the sole reason
# "pending FOLD-MIGRATE". All five FOLDED 2026-08-10 (FUSION-DENSE-MIGRATE, issue
# #299, specs/fusion-dense-migrate.md) onto layers::UnquantizedMlpGateUpMethod, so
# their entries are GONE and re-adding one is a REGRESSION the checker now catches
# (tests/scripts/test_check_fusion_consistency.py::test_folded_dense_models_stay_folded).
# What is left below all names a blocker that needs the SHARED LAYER extended --
# an f32 arm, a bias arm, a keep-quant arm, a GeGLU arm on the grouped MoE op, an
# NVFP4-Marlin-resident arm, or a residency arm -- which is its own row, not a
# model fold. A bare "pending <ROW>" is NOT a reason: that is exactly how this
# allowlist grew to hold most of its population, so an entry states the arm the
# shared layer is missing.
# glm4 and phi3 remain on the OTHER allowlist (scripts/fusion-consistency-allowlist.txt)
# for the unrelated GLUE floor (add+RMSNorm -> vt::FusedChain), tracked by #314; #299
# closed the merged-GEMM half only.
gemma4_vision   # GeGLU vision-tower MLP -> UnquantizedMlpGateUpGeluMethod + a clamp-epilogue hook (Tier C2); pending FOLD-MIGRATE
gemma4_moe      # known-drift pending fold. BLOCKER (a GeGLU arm on the grouped MoE op): every GeluAndMul here is a per-EXPERT routed-MoE epilogue over raw expert-slice pointers -- ExpertGeGLUHost (host upload), ExpertGeGLUDeviceAccum (device view + alpha/beta accumulate-into), ExpertGeGLUFp8Native (MatmulBTFp8Channel), and the top-k batched fused-Gelu -- and NEITHER shared arm reaches that shape. layers::UnquantizedMlpGateUpGeluMethod is the DENSE arm: one OwnedTensor in, a fresh DBuf out, with no expert slice, no accumulate-into and no fp8-channel GEMM. The shared grouped op vt::MoeGateUpSwiGLUGrouped is SwiGLU-only AND wants the stacked [E*N,K] towers in a CUDA keep-quant dtype. Folding means giving the grouped MoE op a GeGLU (and accumulating) arm, which is a shared-layer change, not a model fold.

laguna  # known-drift pending fold. BLOCKER (an NVFP4-Marlin-resident arm): the two detected vt::SiluAndMul calls are the LEVER-B epilogue of vt::MoeGroupedGemmNvfp4Marlin over the N-concatenated w13, held as RAW DEVICE POINTERS in LagunaMoeMarlinResident (Marlin-repacked i32 weights / u8 scales / f32 global scales owned by the resident decode graph) -- not an OwnedTensor gate_up. Neither shared arm reaches it: layers::MlpGateUpMethodBase takes an OwnedTensor, and vt::MoeGateUpSwiGLUGrouped wants the stacked expert towers in a CUDA keep-quant dtype (Q8_K-quantized activations), not NVFP4-Marlin planes. Folding means an NVFP4-Marlin-grouped arm on the shared MoE op plus a resident-pointer residency arm, and it lands with the decode/runtime framework-routing port (AGENTS.md 3rd seam), not as a model fold.

minimax_h3_device  # known-drift pending fold. The DTYPE half of this blocker is now GONE: the H3 device forward uses TRUE bf16 activation storage, so it matches the seam's kBF16 DBufs. What remains is WEIGHT RESIDENCY: layers::UnquantizedMlpGateUpMethod takes an OwnedTensor (host bytes staged on demand via ResidentWeight), whereas H3 stages device tensors UP FRONT in StageMiniMaxH3DitWeights and binds plain views -- a different ownership model, not a dtype mismatch. H3's fc1 ALREADY ships merged [2*ffn, H] and is ALREADY one MatmulBT, so nothing is unmerged; adopting the seam means moving H3's loaders onto OwnedTensor residency, which is an architectural change to the quantized loaders rather than a fold.

minimax_h3_video_vae_device  # deliberately-not-merged: the video VAE's mid-block feed-forward already ships w1 as a MERGED [2*ff_inner, dim] operand and already issues ONE MatmulBT, so nothing here is an unmerged gate/up pair -- the epilogue is the only hand-call. It cannot take layers::UnquantizedMlpGateUpMethod for two reasons the seam does not carry: the VAE runs the whole block in f32 (DType::kF32 activations end to end, deliberately, because it is a decoder whose output is pixels rather than logits) while the method's DBufs are kBF16, and every VAE Linear carries a rank-1 bias the bias-free method has no slot for. Same weight-RESIDENCY blocker as minimax_h3_device besides: the DiT stages device tensors up front and binds plain views rather than OwnedTensor/ResidentWeight. Adopting the seam means giving it an f32 arm and a bias arm, which is a shared-layer change, not a model fold.

minimax_h3_encoder_device  # deliberately-not-merged: the H3-Encoder's gate/up are ggml BLOCK-QUANT weights (the 32B tower is kept in Q4_K/Q6_K so it fits a 122 GB box), and layers::UnquantizedMlpGateUpMethod is by name and by contract the UNQUANTIZED arm -- it takes an OwnedTensor of plain bf16 and has no block-quant path. Worse, the shipped Q4_K_M checkpoint keeps gate/up UNFUSED whenever the group mixes encodings, so there is not always a single merged [2I,H] operand to hand a merged-GEMM seam at all. Adopting the seam here means giving it a keep-quant arm, which is a shared-layer change, not a model fold.

minimax_music3_device  # deliberately-not-merged: there is NO unmerged gate/up pair here. Upstream's `ff.net.0.proj` is ONE nn.Linear producing [2*ff_inner, inner] which `.chunk(2,-1)` splits (transformer_minimax_music3.py:142-143), so the DiT already ships the merged operand and already issues ONE vt::MatmulBT -- the epilogue is the only hand-call, and a merged-GEMM seam has nothing left to merge. It cannot take layers::UnquantizedMlpGateUpMethod for three reasons the seam does not carry, each of which is a shared-layer change rather than a model fold. DTYPE: the whole acoustic half is f32 by upstream's own choice (spec §2.1) and the method's DBufs are kBF16, so adopting it would narrow a tensor this row is required to keep wide. BIAS: `ff.net.0.proj` and `ff.net.2` both carry a rank-1 bias and the bias-free method has no slot for one. RESIDENCY: the method takes an OwnedTensor staged on demand via ResidentWeight, whereas StageMusic3DitWeights uploads device tensors UP FRONT and binds plain views -- the same ownership blocker minimax_h3_device and minimax_h3_video_vae_device already record. There is a fourth, smaller mismatch worth naming so it is not rediscovered: upstream computes `value * silu(gate)` with the VALUE half first, the opposite assignment to vt::SiluAndMul's `silu(first) * second`, which this file resolves by exchanging the two row blocks of the projection ONCE at stage time.
